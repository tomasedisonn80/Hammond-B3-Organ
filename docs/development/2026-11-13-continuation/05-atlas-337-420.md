## Near-term engineering requirements for M3

1. **Expose the states that distinguish the mechanisms.** Page 369 explicitly asks
   for contact conductance, one shared percussion charge, source phase and routing
   masks through an offline diagnostic interface. Extend the current same-thread
   copied diagnostics to cover the new contacts and readiness state. Store trace
   files outside processing; a future concurrent UI needs a separate verified
   publication mechanism (pp. 379–381, 388–389).

2. **Keep a canonical timeline through every extension.** Retain the existing
   unsigned render clock, stable same-time order, half-open intervals, preflight
   rejection and disconnected-output evolution. A zero-frame flush may update
   targets but must not move contacts, percussion readiness or any other dynamic
   state. No incoming event or inserted empty call creates elapsed recharge time
   (pp. 370, 387, 393, 400). Define sample-order semantics before writing tests.

3. **Use independent behavioral oracles.** At a fixed sample rate, render the same
   contact/percussion sequence over blocks 1, 17, 64, 257 and an irregular partition;
   compare stage states as well as audio. Existing supported rates are 44.1, 48 and
   96 kHz; the atlas's additional rates are proposed coverage, not permission to
   advertise unimplemented rates. Across rates compare common physical times and
   declared tolerances, not unequal sample arrays. Include controls that fail a
   note-reset oscillator or per-note percussion implementation (pp. 369–372).

4. **Protect the existing parameter contract.** The source proposes 62 controls
   and a different numeric layout (pp. 397–402), while the inspected repository
   has 39: 36 integer drawbars, expression at ID 8192 and bank selection at 8208/8209.
   Extend this registry without renumbering current identities. In particular,
   copying an atlas percussion ID into the currently occupied expression range
   would change meaning. Continuous drawbar travel, physical expression and native
   host queue interpolation require explicit compatibility work; the current
   integer/linear-gain contracts must not silently acquire those meanings.

5. **Version control persistence without storing transient musical activity.**
   Add independent percussion settings to musical snapshots, with explicit defaults
   when reading historical `B3CONTROLS1` fixtures. Do not serialize live key owners,
   contact travel, readiness, generator phases or frame clock as if a preset were a
   complete render checkpoint. Invalid/newer state must fail before mutation;
   successful control restore must preserve dynamic state according to its declared
   contract (pp. 389, 394, 401). Parsing and serialization remain outside processing.

6. **Keep eligibility separate from stored controls and physical contacts.**
   Percussion enable/level/decay/harmonic remain retained even if the selected route
   is ineligible. The upper-B 1-foot audible mask must not zero its stored drawbar
   value or erase the physical contact used by the detector. Cancel changes routing
   without creating key releases; lower-manual/pedal controls retain their own
   ownership (pp. 389, 410, 416, 418).

7. **Normalize note ownership before contacts when an external adapter arrives.**
   Input bus/device/channel/note identity must map into bounded physical-key
   ownership. Releasing one owner cannot release another owner's hold of the same
   pitch. Editor close releases only editor-owned notes. The present direct physical
   key API is a useful core contract, but not a complete multi-device/host ownership
   adapter (pp. 392, 412, 417). State an explicit repeated-unidentified-note policy.

8. **Retain a named nominal model and its identity in evidence.** Source and
   contact profiles must identify normalized boundaries, assumed values, fixed
   timing and algorithm versions. Unknown physical quantities remain unknown;
   choosing a supported surrogate makes computation executable, not measured.
   Record the model/configuration alongside source/profile/render hashes so new
   contact/percussion output cannot be mislabeled as the old ideal-only renderer
   (pp. 355–358, 386, 408).

9. **Test bounded runtime behavior after adding per-contact state.** Fixed arrays
   avoid callback allocation, but `noexcept` and source inspection do not establish
   deadlines. Exercise dense two-manual changes, long decays, rejected input and
   zero/disconnected calls. Keep allocator evidence, sanitizer results and any
   measured timing report separate; retain exact compiler, hardware and stimulus
   identities for performance results (pp. 379–384, 388–390).

## Data/acquisition work that can proceed independently

An initial acquisition manifest and validator are useful without acquiring hardware.
Use explicitly fictional/planned records: no invented serials, capture timestamps,
physical measurements, filenames or hashes. Distinguish a planned record from a
recorded acquisition and a synthetic software fixture (pp. 355–356).

A recorded manifest must bind actual bytes to specimen/revision, acquisition group,
channel identities and file indices, raw and qualified clock rates, synchronization,
signal boundary, load, ADC calibration, controls, warmup/environment and permission
references. Validate digests, sizes and WAV headers against files; checking the
shape of a SHA-256 string is insufficient (pp. 350–358). Preserve derivation parents,
operations/tool versions and raw originals. Future whole-corpus validation must
check ancestry cycles and inherited acquisition grouping; adjacent windows are not
independent holdouts (pp. 354, 359, 366).

Do not reuse the factory G–G meter table for oscillator amplitudes, use a nominal
speaker impedance as a full load model, or infer mechanical acceleration from
acoustic phase spikes at cancellation nulls (pp. 337, 346, 350, 361). These require
specific documentary or physical evidence, not more synthetic tests.
