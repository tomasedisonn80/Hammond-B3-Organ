## Immediate M3 implications for the existing code

1. **Continue the working foundation.** The current prepared `Engine`, shared
   source bank, half-open events, non-advancing flushes, retained drawbar banks and
   offline renderer already implement useful portions of the first engineering
   milestones. The next dependency-ready task is the contact/percussion layer,
   not another renderer scaffold (pp. 446–447, 450, 492).

2. **Implement contacts before summing shared sources.** Page 447 explicitly
   requires ordered contact trajectories followed by source aggregation; p. 464
   preserves distinct contacts even when foldback selects the same oscillator.
   The current boolean-key array is a useful ideal mode but cannot represent
   partial release or a different ninth-contact state. Preserve that mode as an
   explicitly named regression baseline while adding nominal trajectories.

3. **Keep one continuous percussion history.** Preserve the physical 1-foot
   keying contact while masking its audible upper-B contribution. Last-key
   release must allow elapsed recovery rather than reset readiness immediately.
   Cancel and bank/tablet changes affect routing without manufactured note-offs
   or source-phase resets (pp. 447, 464). Exact held-note switching remains a
   capture/circuit gate; a reproducible nominal policy is a permitted surrogate.

4. **Preserve stored controls independently of eligibility.** Inactive-bank
   editing must address that retained bank. A percussion tablet retains its
   setting when routing makes it ineligible. Editor selection and sounding
   selection are separate concepts; Cancel and software panic remain separate
   commands (pp. 433–434, 440, 442). Avoid mutating stored 1-foot drawbar values to
   implement an audio mask.

5. **Add diagnostics that can test these distinctions.** Expose copied contact,
   routing and readiness state with sample-frame identity. Existing same-thread
   diagnostics are a suitable initial scope; they must not be described as a
   concurrent UI telemetry protocol. Future snapshots require bounded transport,
   profile/port/time identity and explicit stale/lost coverage (pp. 423, 425, 453).

6. **Extend compatibility deliberately.** The atlas's 62-entry parameter
   registry is a proposal; p. 442 explicitly says it is not a frozen production
   export. Preserve the repository's already assigned 39 control identities when
   adding percussion. Version saved-control migration; saved controls must not
   become an implicit exact DSP checkpoint (pp. 450, 456, 468).

7. **Close a scoped checkpoint, not all of M3.** Contacts and percussion alone
   leave pedal audio/control integration, full preset latch masks, continuous
   drawbar travel and loaded expression work. The concluding M3 checklist names
   those independently (pp. 447, 454, 464). M5 later replaces the surrogate while
   retaining the tested event semantics (p. 447).
