## Concrete MIDI requirements derived from this reading

### Ownership must survive UI activity

Pages 434, 438, 461 and 485 explicitly require external MIDI ownership to survive editor absence, focus changes and rendering trouble. A note's press captures its original owner/target; release uses that record. Internal focus changes and resizing are not note-off events. Page 442 additionally separates musical commands from focus, tabs and decorative motion.

For the currently selected adapter design:

1. Reserve internal UI channel zero and document the external upper/lower/pedal owner namespaces. Configuration selects three distinct wire channels from 1-16, with unrelated channels ignored and counted under the stated policy.
2. Deliver backend messages into a bounded inbox. Only the existing main-thread producer calls `Session::post`; never add an independent backend producer to that single-producer queue.
3. Preserve ordering of accepted messages and freeze arrival/timestamp/late-event behavior. Current offset-zero Session semantics are callback-boundary delivery; a backend timestamp is diagnostic input, not evidence of sample-accurate scheduling.
4. Match Note On velocity zero to the declared release path. Preserve source phase and existing steady loudness law. Document duplicate Note On/repeated-pitch behavior and retained route policy before tests.
5. Define CC120, CC121 and CC123 separately and make each control's target/range explicit. A controller message cannot silently bypass current parameter identities or turn a scoped release into global Panic.
6. On disconnect/restart, release only device-owned notes through a bounded declared path; UI notes remain owned. A full Session transport failure retains its existing global emergency policy and must be reported distinctly.
7. Quiesce and join backend callbacks before queue reset or destruction. Allocation, device enumeration, error formatting, connection and handle disposal stay outside audio processing.

### Independent behavior cases worth executing

| Scenario | Required observation |
| --- | --- |
| UI and MIDI hold the same upper note, then UI loses focus | The UI owner releases; the MIDI hold continues until its own release. |
| MIDI and UI notes span upper, lower and pedals | Releasing/disconnecting the device does not release UI owners or alter retained controls. |
| Configured wire channels include 1 and 16 | Both follow declared reserved internal namespaces; neither aliases UI channel zero. |
| Two configured channels use the same value | Configuration rejects atomically; it does not silently change a held note's route. |
| Note On velocity zero, duplicate On, unmatched Off | Each follows the frozen policy, with bounded owner count and no stuck notes. |
| Equal timestamps, late timestamp, malformed length/status/data | Stable documented order or explicit rejection/counter behavior; no fabricated sample precision. |
| Inbox overflow with held notes and subsequent restart | No stranded device holds or stale replay; failure/recovery counters explain what happened. |
| UI modal, resize and rendering pause during external chord | Sound/ownership continue independently of window state. |
| Shutdown concurrent with backend delivery | No access after retirement; joined close and bounded queue lifetime are demonstrated. |
| External controllers adjust drawbar/expression while UI edits another bank | Correct retained parameter changes; editor selection does not silently choose the sounding route or overwrite unrelated controls. |

These are recommended acceptance cases, not tests executed by A06. Parent integration owns the final contract and exact expected outcomes.

## UI and reference-matching implications

### Preserve artistic target and truthful controls together

The [exact retained cover reference](../../design/atlas-cover-reference.jpg) provides the visual target selected by the integrator. Its cabinet, wood cheeks, dark panels, brass trim, cap relief and key fronts can guide the native rendering. Page 431 explicitly warns against copying its incorrect controls. Therefore a useful reference-oriented implementation should retain the existing 61+61 playable notes, 25 pedals, 36 retained manual drawbar positions, two pedal controls and stable musical meanings even when their visible arrangement differs from the generated art.

The product distinction is concrete: cabinet art may be decorative; requested speed, simulated speed and unavailable audio processing must not be presented as interchangeable states. Page 437 states that stopping a visual rotor is not an audio brake command. Pages 421-426 disallow convincing decorative illustrations from becoming a live-engine or measurement claim.

### Layout and interaction requirements

- **Keep control text readable first.** Page 436 specifies collapsing the cabinet preview before shrinking labels. A small-width layout should reflow or omit that decorative area while keeping active controls and status reachable.
- **Use one layout transform.** Painted bounds, hit testing and future native accessibility bounds must agree, including scale changes. Window resize must preserve focus and musical ownership.
- **Keep labels separate from raster art.** Page 430 calls for readable labels composited independently of scene exposure. Raster controls with frozen text or state would defeat the semantic requirement.
- **Preserve distinct cues.** Edited bank, sounding route, selected value, focus and percussion eligibility are different states. Color alone does not convey them (pp.433-435).
- **Keep retained bank identity.** A hidden editor bank is not a hidden host parameter. Bank switching closes a captured edit gesture before rebinding, and a gesture's end targets the original ID (pp.433,441-442).
- **Keep flat operation complete.** Page 437 requires a usable alternative skin rather than an error display. A decorative-resource failure must not prevent playing, editing or emergency recovery.
- **Separate keyboard usability from native accessibility.** Existing keyboard navigation is useful but does not expose a platform accessibility tree. Actual screen-reader workflows, announcements and value editing remain separate qualification (pp.433,438).
