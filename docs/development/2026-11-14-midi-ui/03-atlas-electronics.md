## Nonnegotiable UI semantics from this range

1. **Routing and selection are separate controls.** PDF p. 169 gives four tablet combinations: off/off routes U+L+P dry; Swell only routes U to the scanner; Great only routes L+P; both route U+L+P. Q, percussion, bypasses the scanner in every case. The historical six choices are V1/V2/V3/C1/C2/C3, with bypass controlled by tablets.
2. **Physical knob arrangement is not the semantic enum.** The inspected p. 170 P010 photograph shows separate normal/soft volume, vibrato Swell and vibrato Great tablets beside the six-position selector. Its printed photographic description orders positions `v-1,c-1,v-2,c-2,v-3,c-3`. Implement explicit mappings rather than relying on display index or enum ordinal. The photograph is hardware/source evidence, not an already delivered application screenshot.
3. **Depth means a connection map.** The p. 170 maps are exactly `[1,2,3,4,5,6,7,8,9]`, `[1,2,3,5,7,9,11,12,13]` and `[1,2,4,7,10,13,16,18,19]`. V/C at a depth share the map; their return topology differs. Smoothly interpolating these source-node indices or presenting the three depths as three arbitrary sinusoidal delay amplitudes changes the model.
4. **No accidental historical claims from product labels.** The current renderer remains nominal and unmeasured. Displaying a wooden chassis, realistic tablets or valve imagery does not make scanner, AO-28, headroom, aging or Leslie controls operational. Current nominal expression is a gain surrogate; p. 251's loaded physical expression behavior is a future circuit/acquisition task.
5. **State survives presentation.** The source, scanner and connected reactive histories do not reset with note-on, selector movement, window resize, focus changes or editor closure. Control-only persistence is separate from transient DSP/ownership history. A cosmetic profile is separate from the physical model and service record (pp. 172, 184, 226, 234, 244).
6. **Service evidence must keep disagreements.** If a service view is added, p. 239 requires source conflicts to remain serialized and visible: factory C59 versus redraw C56, duplicate catalog 6-6-43, unresolved item 47 and mutually exclusive AO-28 alternatives. Unknown cannot be rendered as zero or a confidently fitted value.

## MIDI continuation: actionable contracts and a discovered ownership risk

The read [Session interface](../../../apps/standalone/Session.h) identifies one main/UI producer and one serialized audio consumer. Its public commands currently admit **offset zero**, apply a frozen FIFO prefix at the next callback boundary, and make accepted versus applied commands distinguishable. [PerformanceInput](../../PERFORMANCE_INPUT.md) preserves supplied ordering, uses whole-call admission, and coordinates manual/pedal ownership with one Engine timeline.

That architecture supports a next M9 external-input adapter, with these conditions:

- Marshal device input through the existing producer owner. Calling `Session::post()` from an independent MIDI callback would violate the published single-producer contract even if a simple test appears to work.
- Freeze what timestamps mean: acquisition time, queue order and the existing callback-boundary delivery are different quantities. Do not claim sample-accurate hardware delivery merely because backend events contain timestamps. A later scheduler must explicitly address late events, clock conversion, equal-time ordering and callback boundaries.
- Preserve original owner identity through routing/target changes. PDF pp. 248–249 requires coherent source reuse and repeated-pitch ownership that does not manufacture a second physical press while the key remains held. Velocity is at most input to a declared gesture approximation; it is not a measured nine-contact trajectory.
- Test independent UI and device owners on the same note, repeated note-on and velocity-zero release, channel ownership, original-route release, channel panic, global panic, disconnect and restart. Disconnect must release the relevant device owners without clearing UI-held notes or resetting source phase.
- **Resolve the 16-channel collision before implementation.** `kUiInputChannel` is zero; `ReleaseUiNotes` is explicitly scoped to that channel across origin buses. Simply placing external MIDI channel 1 (zero-based channel 0) into that namespace allows ordinary UI focus loss to release device notes. Silently remapping or dropping one channel is not a complete 16-channel design. Choose an explicit source/owner namespace and scoped-release policy, or state and test a deliberately restricted supported mapping. This is an interface-design issue, not an established defect in the pre-MIDI app.
- Retain bounded admission and failure recovery. A full queue must not drop the only note-off, spin in the audio thread or partially apply a gesture. Report the actual degradation/recovery state through copied observations.

Useful timing acceptance comes directly from p. 252: express one absolute logical sequence under multiple block partitions, include first/last sample edges, preserve same-time order, and distinguish cross-rate reconstruction from byte equality. The atlas proposes 44.1/48/96 kHz and block sizes 1/17/64/127/512/1024; acceptance must also reflect the product's actual supported contract. These are proposed fixture settings, not measured latency limits.

## What remains blocked and what can proceed

The inspected [scanner handoff](../../SCANNER_HANDOFF.md) retains the G5 same-hertz failure at every allowed research rate and explicitly bars premature Engine integration. That failure must remain visible; M9 input/UI work neither causes nor clears it.

M5 requires a selected revision, independent complete connectivity, resolved active values, source/load definitions, transformer/operating-point evidence, a loaded small-signal reference, then bounded nonlinear qualification. The atlas supplies neither the completed graph nor physical captures in this page range. The currently unmeasured quantities must remain unknown or explicitly provisional.

The dependency-ready continuation is therefore external input ownership/lifecycle plus truthful native UI refinement against the stable dry core. Preserve the existing 45 parameter identities, control-file migration, native UUIDs, source/profile bytes and independently owned research tracks. New device/build provenance, concrete runtime checks and actual application screenshots can advance product engineering now. Physical controller timing, complete electronics, native accessibility and exact visual-match claims still require their own observed evidence.
