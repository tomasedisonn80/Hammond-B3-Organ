## Concrete implications for M3/M9 continuation

1. **Console behavior can advance with retained software evidence.** Pages 49-54 provide clear behavioral requirements for editing inactive banks, changing selectors during sustained notes, canceling only the manual route, preserving expression through registration changes, and independently controlling global Soft versus percussion Soft. Verify these against existing session/UI code before adding a control or changing a gesture. Existing 47 parameter identities, `B3CONTROLS4`/readers 1-3 and note/phase/percussion histories remain standing repository compatibility constraints.
2. **A UI improvement must preserve one state system.** Pages 34 and 40 require a bounded read-only visual view of audio-owned state. Resize, reduced motion, panel visibility and flat/perspective presentation cannot alter route selection or source time. Pages 49 and 54 require explicit values, semantic control identities and a selected state that matches actual sound. These requirements make a usable control/navigation improvement independently testable without claiming electrical calibration.
3. **Registration persistence is a musical distinction.** Page 50 treats modern total-state snapshots as a separately named software layer; p. 51 retains expression when changing registration. A browser must make registration/performance behavior clear and preserve inactive banks. Existing repository contracts may intentionally distinguish generic full-state Load from scoped Registration recall; retain that distinction.
4. **Reference-match work requires actual captures.** Pages 31-36 and 53-54 call for silhouette/layout, material provenance, readable control legends, correct physical inventory, disabled-animation use and geometric uncertainty. Preserve the user's literal 1:1 target, but do not label a narrow regional improvement whole-interface equality. The rendered p. 49 photograph is colored stage-light context, not an absolute color standard; the designated concept art remains the UI direction.
5. **Audio model expansion cannot be justified by UI readiness.** Pages 4, 12, 73-84 require distinct observation boundaries and forbid downstream tuning that conceals an upstream error. The nominal dry Engine remains the coherent default until separate live-integration contracts and evidence authorize another route.
