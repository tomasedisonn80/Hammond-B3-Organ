### Audio and ownership oracle

The paired case first advances silent audio before any note. Upper 60, Lower 55
and pedal 13 each acquire two independent owners, with different origin/channel
identities. One side receives the model's returned copied control effect; the
other receives the explicitly expected control values. The third Engine receives
only the intended physical NoteOn/NoteOff/PedalOn/PedalOff transitions, rather
than Session's ownership or command dispatcher. Every rendered stereo sample is
compared bit-for-bit across the two Sessions and with that Engine's mono sample.
Both Session snapshots are compared field by field after every render, including
actual holds, counters, controls and frame clock.

For all 91 sources, the expected phase starts from the prepared seeded phase and
advances by the independently calculated profile frequency/sample-rate increment
once per frame, including silent and disconnected routes. Immediate control and
physical-note transitions must leave those phases unchanged. The separately
calculated nominal percussion decay/recharge recurrence is checked with an
absolute `2e-11` readiness tolerance, matching the existing continuity protocol.
Expected audible blocks must have peak above `1e-7`; expected silence is exact.
These checks specifically prevent output equality from passing merely because
all outputs are silent. Numerical tolerances were not relaxed for this suite.

This establishes a test oracle for the returned copied effect's Session boundary.
It does not claim access to hidden Session phase fields, a new physical model,
the future UiModel named-recall helper, browser input routing or native adapter
integration. No production Engine, musical parameter, state format, source clock
or owner implementation is changed.

## Resolved-versus-applied interpretation review

During authoring, root reported A16's first pure gate as 31/32 groups with one
disputed synthetic expectation. Independent Session source inspection found:

- A successful consumed command advances both `resolved_sequence` and
  `last_applied_sequence` before publication.
- A consumer failure advances resolution but not application for that command,
  increments rejection, discards the remaining prefix and increments recovery
  before the coherent callback publication.
- Queue recovery, Stop and Prepare advance resolution through discarded slots
  and increment discard history. A consumed/discarded command cannot later
  apply; a higher subsequent applied sequence belongs to another command.

Consequently a newer publication with neither sequence covering the control is
a legitimate wait. A publication resolving the control without application
cannot later justify that original intent. I reported this distinction to root
and read back root's narrow A16 amendment: its first branch now waits without
sequence resolution; its separate resolved-only branch requires terminal
Unconfirmed and refuses revival by a later applied sequence. I agree with that
interpretation. I did not edit A16 or LibraryModel. Root retains the original
failure and original source identity. A19's real failure paths require Rejected
from their actual changed counters, rather than fabricating the pure model's
counter-free resolved-only snapshot.
