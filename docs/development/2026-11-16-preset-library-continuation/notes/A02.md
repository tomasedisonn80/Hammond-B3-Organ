## Recommended bounded next phase: inspect/export and a proposed pack

Root's candidate is supported by pp. 122, 126 and 155: make persisted controls
inspectable and portable with explicit scope, without adding a new live state
owner. A small native CLI can consume the already published storage and control
APIs, enumerate a complete bounded catalog, inspect a selected valid entry, and
materialize a deliberate ordinary-control export. A small checked-in pack can
provide useful named software registrations for that flow.

Freeze these decisions before implementation:

1. **Inspection is read-only.** Report stable filename key, scope, entry status,
   catalog completeness/warnings, all four nine-digit banks, both pedal values,
   remembered/fixed/route state, percussion, expression treatment and the frozen
   catalog identity. Invalid and ambiguous rows stay diagnostic; missing root
   inspection must not create a directory. Never call inspection an applied or
   sounding registration.
2. **Reuse musical admission.** Use the existing parser/serializer and pure
   merge helpers. Do not add a second hand-maintained parser for versions 1-4.
   A selected export needs a complete scan and a valid, unambiguous exact key,
   followed by fresh bounded entry read; `read_registration_entry` alone does
   not establish catalog-wide case uniqueness.
3. **Specify expression at export.** Generic `--state` Load restores the full
   parsed snapshot regardless of `.b3registration` suffix. To materialize
   Registration semantics, require an explicit validated base/current-controls
   input and merge its expression before serialization, or clearly expose a
   different full-controls export operation. A standalone CLI cannot know the
   application's live desired expression. Performance includes saved expression.
   Do not claim that a suffix makes generic Load scope-aware.
4. **Define an offline transaction.** Exported bytes come from validated file
   input, not a Session acknowledgment. Reusing create-only storage must retain
   its protected-path, no-overwrite, fresh admission and committed-with-warning
   behavior, with an explicitly reviewed offline authorization basis. Never
   assert that an offline export observed or saved live audio controls. Keep
   inspect/list free of mutation, and separate stdout reports from diagnostics.
5. **Keep the pack proposed and complete.** Use ordinary canonical controls and
   portable admitted names. Explicitly set every bank, retained mode, route,
   pedal value, percussion control and expression payload. Include plain-language
   intended uses and scope, but no measured/factory/person-specific attribution.
   Preserve the frozen chapel matrix and digest. New examples add no automatic
   startup recall, legacy default, Engine route or parameter identity.

Useful acceptance consists of literal field expectations for every pack entry;
native parse/serialize round trips; Registration versus Performance expression
cases with a nondefault base; legacy versions and malformed/future/corrupt catalog
rejections; leading-zero preservation; cancelled-manual retained memory; missing,
invalid and ambiguous library entries; exact capacity edges; output/input aliases
and existing-output preservation; and an actual supported standalone Load of a
produced file. Preserve the result's true scope: file/export usefulness and state
compatibility, not audio-history continuation or a completed native library UI.
