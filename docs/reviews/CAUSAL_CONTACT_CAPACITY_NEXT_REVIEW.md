# Continuing contact capacity: independent proposal review

**A51 (`/root/w09_a51`), 16 November 2026.** The arithmetic and the cited
current-source distinctions in [A40's proposal](../research/CAUSAL_CONTACT_CAPACITY_NEXT.md)
are supported, subject to the explicit conditions below. **This admits a
planning calculation, not a full-organ design, continuing API, storage fit,
callback deadline or physical model.** No implementation is authorized by this
review. Root retains architecture and integration acceptance.

The principal remaining requirements are a precisely scoped input/transaction
window, separate hard-panic semantics, a nonsealing zero-time update, retained
history with checked clocks, and complete audio/host storage and work proofs.
The counterexamples below concern possible extensions; none is a newly observed
defect in the finite `causal-contact-grid-v1` implementation.

## 2. Manual expansion bound: valid under a named authority

For the existing manual owner state, let `I` be the number of physical keys with
at least one owner at transaction entry, `P` the number of emitted first-owner
Ons, `O` the emitted final-owner Offs, and `F` the final number of owned physical
keys. Every emitted On raises that count by one and every emitted Off lowers it
by one, so

`O = I + P - F`, and `M = P + O = 2P + I - F <= 2R_manual + 122`.

Each first-On requires its own positive raw On record. A scoped panic may emit
many Offs but cannot consume a physical owned key twice without an intervening
first-On. Duplicate IDs, anonymous overlap, zero-velocity releases, missing
releases and bus remapping do not break that conservation argument: the counted
identity includes the original manual. `I<=122` follows from physical keys,
independently of the 256-owner limit.

For HostTimeline, `R_manual` can conservatively be bounded by the one captured
callback budget `R`: fresh musical records plus all fresh parameter points plus
retained raw carry, at most 1,024. Restores are separately limited to four and
preserve key/owner history. This yields `M<=2,170`; it does **not** assert that
all admitted raw inputs actually emit that many targets. Each individual
NoteOwnership translation and PerformanceInput's combined block still reject
physical output above 1,024. HostTimeline translates one raw note at a time and
can stage multiple candidate Engine calls.

**Constructive callback witness.** At offset zero repeat 16 times: press every
Upper note 36–96 on bus 0/channel 0 once, then send that scope's AllNotesOff.
There are `16*(61+1)=992` raw records, at most 61 simultaneous owners, and
`16*(61+61)=1,952` emitted transitions. All payloads and owner transitions are
legal for HostTimeline, whose bounded zero-frame flushes handle the expanded
group. This is a source/closed-form witness, not a native run. Supplying the
same sequence as one NoteOwnership/PerformanceInput translation exceeds their
output cap and rejects. A generic “1,024 events” assertion cannot replace the
adapter-specific contract.

### A51-C1: do not apply the owner proof to other command expanders

The inequality requires that every supplied manual target correspond to one
of those emitted physical transitions, or that extra target records receive a
separate explicit charge. Counting raw inputs and then silently adding repair,
rebase, direct physical or panic targets breaks its premises.

For example, three legal direct Engine AllNotesOff records on one manual, if
naively expanded into all 61 target-zero records each, supply `M=183`, including
no-ops, while `2R+122=128`. This is a counterexample to that hypothetical general
expander, **not** to the ownership-only proof. The proposed ordinary targets also
cannot implement Engine's immediate panic: ContactBank clears positions,
targets and bits even for a key whose released target still has travelling
contacts. A scoped owner release deliberately preserves other owners and uses
ordinary release travel. They need separate semantics and quotas.

Before using the bound as an admission limit, freeze:

- One captured raw prefix and one persistent, coordinated note authority;
  carried records are counted once in the accepting callback. Do not reset a
  callback quota for each internal slice or independently admit producer queues.
- The exact map from owner transitions to supplied targets, including no-ops,
  ties, boundary updates and any converter-generated records.
- Whether direct KeyPosition, direct Engine notes, manual/global hard panic,
  Session recovery and profile changes are excluded or separately charged.
  PerformanceInput currently rejects a physical/partial-key bypass.
- Pedal and control bounds. For the existing owner transition domains together,
  the analogous count is at most `2R_musical+147`, but it is neither a manual
  nine-contact edge bound nor a bound on generated control automation.

## 3. Edge bound and work bound require different qualifications

With valid retained trajectory history, fixed thresholds/speeds and only the
current target operation, a monotone movement crosses each contact at most once.
There are at most `A` unfinished incoming movements and at most `M` new movements.
Thus `E<=9(A+M)<=9(K+M)` is correct. It includes supplied tied/no-op commands
conservatively; it does not require an oscillator or history per owner.

**Incoming-motion witness.** In the admitted one-key domain, use speed 1,
all nine contacts `off=0,on=65,537`, and target `Q=2^48` at tick zero. After one frame
the key is at 65,536 with open bits. The next command-free frame emits all nine
edges at tick 65,537. Resetting the command counter and reusing `E<=9M` would
give zero incorrectly. The finite epoch's original `9*512` proof charged that
motion to the earlier command; a new window must explicitly retain the `A` term.

This proof excludes arbitrary imported bits, threshold edits, instantaneous
panic edges, bounce/resistance models and implicit time advancement. For any
new boundary/import operation, prove that incoming equality was emitted exactly
once, the contact bits match the retained motion, and commands do not manufacture
an uncharged edge. The admitted v1 API has no arbitrary-state import.

The numerical extrapolations all reproduce exactly:

| One positive call, `K=122`, `M=2,170` | Bound |
| --- | ---: |
| Reached edges `9(K+M)` | 20,628 |
| Key evaluations `K(M+1)` | 264,862 |
| Contact examinations `9K(M+1)` | 2,383,758 |
| Euclidean remainder steps `64E` | 1,320,192 |
| Insertion-sort comparisons `floor((9K-1)E/2)` | 11,314,458 |
| Comparisons in one maximum interval `(9K)(9K-1)/2` | 602,253 |

### A51-C2: the tabulated traversal bound is for one positive call

If a logical window is processed using `C` positive calls, the scanner's
corresponding bound is `K(M+C)`, with `9K(M+C)` contact examinations. For example,
256 command-free one-frame calls scan 31,232 key positions at K=122; one
command-free 256-frame call scans 122. The concatenated edge bound is unchanged
because movement/contact history persists. A proposed scheduler may choose one
call per transaction window, but must state that and account for the number of
windows/slices in each host callback. The smaller single-call formula must not
be presented as a partition-independent whole-callback work bound.

HostTimeline evaluates active curves for up to 47 parameters per sample.
Even one expression endpoint can yield many per-sample control changes; the
raw-record budget does not bound generated automation by 1,024. A conservative
source count is `47*max(1,N)` candidate control events before suppression, in
addition to ownership work. HostTimeline also previews ownership transitions
before actual candidate application. These operations, candidate copies,
publication and rejected/zero-frame calls remain outside A40's grid table.
Arbitrarily repeated external empty/rejected calls have per-call bounds only.

## 4. Zero-time update, closure and commit are distinct contracts

[Engine](../../src/Engine.cpp) accepts valid offset-zero events in a zero-frame
call without advancing source phase, elapsed contact travel, readiness recovery
or the frame clock. Events can still change targets and ideal contact bits, or
perform an immediate hard panic. HostTimeline uses this behavior for dense
same-sample groups and commits live Engine/owners/carry and caller output only
after the complete callback succeeds.

The [grid](../../src/research/CausalContactGrid.cpp) instead accepts
`process(0,{})` as identity and rejects nonempty zero-frame targets. Calling
`close_observation` applies targets but seals the object; the next process call
returns `invalid_state`. Calling `reset` after closure opens all contacts and
zeros positions, targets and anchors. In the incoming-motion witness above,
that loses the nine future crossings. Closure simulates neither release nor
an ordinary processing boundary. The proposed final audio drain must not be
inserted between ongoing windows.

### A51-C3: define one nonfailing publication boundary for the entire route

Required staged state includes ownership, trajectory, replay bits, unfinished
cell pieces, sums/rings, source origins/phases, controls/percussion, all cursors,
host carry and output. Advancing the current grid and then discovering a late
audio error cannot roll back the live grid. Closure has the same problem if
terminal-cell finalization can fail afterward. `snapshot()` is observational,
not restore; copying object bytes is not an admitted API. HostTimeline's
compile-time/value-copy assumptions also do not accept the current noncopyable
grid as a new Engine member.

Freeze the proposed nonsealing boundary operation, equality/tie order, failure
precedence, input lifetime/alias rules, and ownership of both prepared state
copies. Test rejection in a later slice/terminal operation after substantial
candidate work; no live state, caller sample, ownership, carry or published
sequence may move. No-op commands must retain original motion anchors.

## 5. Continuing clocks and retained histories

A40's horizon arithmetic is correct:

| Representation/check | Exact result |
| --- | ---: |
| Existing epoch endpoint `4096*65536` | `2^28` ticks |
| Whole frames representable in uint32 ticks | 65,535 |
| Endpoint of a legal 65,536-frame Engine block | `2^32` ticks, outside uint32 |
| Whole frames representable in uint64 ticks | `2^48-1` |
| Maximum elapsed ticks with uint64 product at speed `2^32-1` | `2^32+1` |

**Naive widening witness.** For an original anchor at zero, target Q and maximum
speed, full travel has arrived by tick 65,537. Nevertheless, the existing
`position_at` multiplication would overflow at elapsed tick `2^32+2` if only its
tick type/domain were enlarged: the unchanged anchor still has target different
from anchor position. This is roughly 65,536 frames after the command, long
before the proposed uint64 tick horizon. It is unreachable within the current
4,096-frame contract. Repeated identical targets intentionally do not repair
the old anchor. Check arrival/clamping before the large product, or prove a
new computational-anchor representation while retaining original observable
command identity.

The continuing contract must also specify exact multipart comparisons,
checked additions for future roots, local-window offset conversion, cursor and
sequence exhaustion, counter saturation semantics, and end-of-clock policy for
the extra output/drain indices. A legal input end near `UINT64_MAX` does not by
itself guarantee room for an additional drain offset; reserve that headroom or
define a separate representable output clock and its failure policy. Injected
near-limit tests are appropriate; elapsed wall time is not a proof.

Do not reconstruct source phase from an ever-growing binary64 frame number:
consecutive integers `2^53` and `2^53+1` have the same binary64 representation.
Preserve all 91 continuously advancing histories across silent/disconnected
intervals and continuing windows, and separately prove the subframe phase
calculation and any bounded computational origin. Engine's frame clock counts
frames across rate changes, not elapsed seconds. Its stopped/same-thread rate
change preserves phases, keys, contact history, readiness and frame clock;
HostTimeline also retains its owners, normalized anchors and carry.
[A38's finite proposal](../research/CAUSAL_CONTACT_AUDIO_NEXT.md) requires
drain/prepare. That policy conflict remains open. Specify the input-time
contact/routing state that drives shared percussion readiness; a delayed audio
output cursor must not become the input/source clock. Control restores, Cancel,
release, hard panic and stop/tail behavior must retain their distinct effects;
saved controls do not serialize DSP history.

## 6. Storage calculation is a subtotal with necessary omissions

Under the expressly assumed ABI/layout and a 24-byte **local-time** edge,
`S(K)=32+192K` gives 23,456 bytes at K=122. I independently reproduced every row:

| Item | Bytes |
| --- | ---: |
| Two trajectory snapshots | 46,912 |
| Transaction edges | 495,072 |
| Interval edges | 26,352 |
| Additional absolute frame fields | 1,968 |
| Caller edge destination | 495,072 |
| Converted target staging | 34,720 |
| Two 8,194-double rings | 131,104 |
| 8,193-double coefficients | 65,544 |
| 256-float output staging | 1,024 |
| **Illustrative subtotal** | **1,297,768** |
| **2 MiB minus that subtotal** | **799,384 unassigned** |

The arithmetic does not establish a new class's ABI size, alignment or peak
stack, a streaming fit, or an application arena. In particular, a global time
representation must explain how local edges retain their window identity without
silently enlarging the assumed record. Full callback output remains staged by
HostTimeline: its current `65,536`-float array alone is 262,144 bytes on the same
four-byte-float assumption, regardless of a proposed 256-frame internal slice.
Count current live/candidate Engine and owner objects exactly once in a declared
application budget; neither omit them nor add duplicate copies by implication.

### A51-C4: cell-piece/summation storage cannot follow from ring length

An admitted finite-grid construction puts all 4,608 edges in one cell's positive
half: four keys, nine contacts each with `off=0,on=1`, both speeds `UINT32_MAX`;
at each tick 0–127 command all four keys alternately to target 1/0. There are
512 supplied targets. Every root is `tick+1/(2^32-1)`, strictly before tick 128;
the positive half of A38's cell zero is `[0,128)` ticks. Each of 36 routes has
64 connected intervals, giving 2,304 connected pieces. The independent receipt
checks these exact fractions/counts; it is not a native/audio run.

Thus 36 simultaneous contacts does not imply 36 pieces per cell. A streaming
accumulator may avoid retaining every piece, but must prove bounded arithmetic,
deterministic summation and identical output under callback partitions. The
full-organ route also requires capacities for exact endpoints, active/open
pieces, shared phases, replay bits, percussion/pedal states, owners, queues,
metadata, host staging and compiler stack. A fixed coefficient table and ring
do not supply those bounds. A38's current initial domain remains four keys and
N/block at most 256; this review does not enlarge it to 122 keys.

Thirty-one current four-key objects cost `31*113,056=3,504,736` bytes before
caller storage. That verified arithmetic provides no global ordering,
cross-object transaction, common quota, continuation or hot-key fairness.
