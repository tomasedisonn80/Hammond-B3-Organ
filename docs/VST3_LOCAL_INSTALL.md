# Local staging and relocation of the native VST3

`NativeVST3` is an explicit CMake install component for a previously built
`HammondB3.vst3` bundle. It copies that complete bundle into a local prefix you
choose, including the linked module, SDK-generated metadata and license notices.
It does not register a plugin, create a link in a DAW scan directory, install SDK
sources or copy the validator/test programs. The optional adapter remains the
nominal engineering prototype described in [VST3_BUILD.md](VST3_BUILD.md).

The component is available only with `HAMMOND_BUILD_VST3=ON`. It is excluded from
an unqualified `cmake --install`; select `--component NativeVST3` explicitly.
The [OfflineTools component](OFFLINE_INSTALL.md) remains independently installable.
Each component has its own preflight and install manifest; installing one does not
require building the other component's executables.

## Build and stage in a chosen local directory

Follow [VST3_BUILD.md](VST3_BUILD.md) to acquire and verify the pinned, external
SDK. Native builds require CMake 3.25+ and the recorded platform prerequisites.
This example fixes the otherwise configurable library directory to `lib`, so the
local destination below is predictable:

```sh
cmake -S . -B build-native -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON \
  -DHAMMOND_BUILD_VST3=ON -DHAMMOND_VST3_SDK_ROOT="$HOME/dependencies/vst3sdk" \
  -DCMAKE_INSTALL_LIBDIR=lib
cmake --build build-native --config Release --parallel 2 \
  --target HammondB3 test_native_abi
ctest --test-dir build-native -C Release -R '^test_native_install$' \
  --output-on-failure
cmake --install build-native --config Release --component NativeVST3 \
  --prefix "$HOME/hammond native stage"
```

Use the SDK path you actually verified. No command in the install operation
downloads dependencies or builds missing inputs. Match the build and install
configuration, especially with Visual Studio and other multi-config generators.
In a Windows developer PowerShell terminal the install step is:

```powershell
cmake --install build-native --config Release --component NativeVST3 `
  --prefix "$env:USERPROFILE\hammond native stage"
```

These are usage instructions, not claims that this assignment executed Windows
or macOS qualification. Its observed platform and source snapshot are recorded
in [assignment 38](development/2026-11-13-pedals/38-install-packages.md).

Choose a new local staging prefix without elevated privileges. If unrelated
files or other bundles are already in that prefix, installation preserves them.
If the destination `HammondB3.vst3` already exists as a file, directory or symlink,
installation refuses before changing it. Use another prefix for another version;
the component deliberately does not merge bundles or remove an old installation.
`--prefix` overrides the configure-time install prefix. `DESTDIR`, if explicitly
set, remains CMake's additional staging root; the acceptance test removes it so
its temporary prefix is the only destination.

## Exact payload and location

The destination is:

```text
<chosen-prefix>/<CMAKE_INSTALL_LIBDIR>/vst3/HammondB3.vst3
```

`CMAKE_INSTALL_LIBDIR` must be relative, nonempty and free of parent traversal or
CMake list separators. Its platform default may differ from `lib`; the example
above sets it explicitly. Absolute and parent-traversing values are rejected.
Leave `CMAKE_INSTALL_MODE` unset or set it to `COPY`. Symlink install modes are
rejected so the installed bundle does not depend on its original build directory.

The source bundle comes from the SDK's actual `SMTG_PLUGIN_PACKAGE_PATH` target
property. It is also recorded in `build-native/hammond-vst3-path-Release.txt` for
the example configuration. Installation copies the directory tree and preserves
source permissions and bytes; it does not reconstruct a platform layout from a
guessed architecture string or rewrite metadata, RPATHs or signatures.

The observed Linux x86-64 Release bundle contains these four files:

| Path within `HammondB3.vst3` | Purpose |
| --- | --- |
| `Contents/x86_64-linux/HammondB3.so` | Actual linked native module, with the compiled nominal profile embedded |
| `Contents/Resources/moduleinfo.json` | Metadata generated by the pinned SDK's module-info tool |
| `Contents/Resources/VST3_SDK_LICENSE.txt` | Pinned SDK's primary license notice |
| `Contents/Resources/THIRD_PARTY_NOTICES.md` | Repository component provenance and notice record |

Other platforms retain the bundle layout produced by their SDK/CMake target,
including `Contents/Info.plist` on macOS. The install test compares the complete
actual file inventory and every file's SHA-256 rather than imposing Linux's
four-file count on another platform. The SDK metadata is treated as opaque bytes:
the pinned tool emits JSON with trailing commas, which a strict standard-library
JSON parser would reject. Byte preservation and actual native loading are the
acceptance criteria here.

No separate authoring profile JSON, compiled profile file, SDK source checkout,
SDK validator, benchmark, source header or native test executable is installed.
The compiled profile is already embedded in the module by the native build.
The ABI test separately receives a copy of the matching compiled profile as its
reference input; it is test equipment, not a hidden plugin runtime requirement.

## Preflight and failure behavior

Before writing any NativeVST3 destination file, installation checks that:

1. The selected SDK bundle exists as a directory, and the selected actual module
   is inside it.
2. The module, generated module-info resource and both notices exist as nonempty
   files. A macOS build also requires its bundle `Info.plist`.
3. The bundle has no symlinks, and the destination bundle does not already exist.

A missing or empty input yields an actionable error before prefix mutation. The
rules validate input presence and layout, not whether a stale binary matches
later source edits; build and qualify the desired revision before staging it.
Installation is not a transactional filesystem operation. A disk-full or other
copy failure after preflight can leave a partial new bundle; retain that failure
and choose a fresh prefix after resolving it. No automatic cleanup removes user
data or another version.

## Relocation acceptance

`test_native_install` is registered only in native-enabled test configurations.
There is no default-build skipped native-install test. All paths and selected
configuration are supplied by CMake; missing inputs fail the gate.

The positive test performs a real component install into a temporary prefix with
spaces. It retains unrelated files and a separate placeholder plugin, requires
an exact native payload with unchanged SHA-256 values, and checks that repeating
the install refuses without changing anything. It then renames the whole prefix
and loads the moved actual bundle through `test_native_abi` from an unrelated
working directory, with all `HAMMOND_*` environment variables removed. The test
requires audible reference agreement and confirms that loading changed neither
the staged payload nor the source build bundle.

The negative test uses a private copy of the built bundle and the real install
module, so parallel native tests retain their original inputs. It checks an
unbuilt bundle, separately missing module/metadata/notices, an empty notice and
invalid destination directories. Every failure must preserve the prefix. It also
checks that an install without `--component NativeVST3` stages no native files.
The copied notices and metadata remain byte-for-byte identical; no test modifies
the shared SDK checkout or actual build products.

The assignment's Linux relocation run loaded the four-file bundle and compared
229,725 native audio frames with zero maximum error against the matched core
reference. This establishes local packaging and actual relocated ABI behavior on
that one host. The retained evidence note records the exact source basis, binary
hash, commands and initial failing offline guard case. It does not establish DAW
scan/session behavior, standalone device support, a clean operating-system
installation, dynamic runtime bundling, code signing, notarization, installers,
hardware fidelity or cross-platform qualification. SDK validation and the wider
native behavioral gate remain separately documented in
[VST3_ABI_ACCEPTANCE.md](VST3_ABI_ACCEPTANCE.md),
[VST3_BEHAVIOR_ACCEPTANCE.md](VST3_BEHAVIOR_ACCEPTANCE.md) and
[VST3_CI.md](VST3_CI.md).
